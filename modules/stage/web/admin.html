Pick standards

Your standard rate for each pick area, one per line, for example Flow = 37. An area with no line of its own falls back to the Other value. Everything any page calls a target comes from here. The picker page can work out what this crew is actually achieving — Recommended standards there — and you type the result in here.

The working week

Days, a name, start to end, then the breaks as clock time = minutes. Shifts, breaks and closed hours all come from this: breaks and closed time are taken out of active time, and a shift ending earlier than it starts runs past midnight. Add setup 20 for the minutes at the start of a shift spent getting a truck, a scanner and a pick list — written once per shift, so second shift gets its own without typing a clock time. It is drawn in orange, not taken out of anybody’s time: a good number of picks land in those minutes, and removing the time while keeping the picks would hand somebody a rate they did not work for.
Example: Mon-Fri 1st 07:00-15:30 setup 20 breaks 09:30=30, 11:30=50, 13:30=30. Blank puts the built-in week back; the word none turns the schedule off.

What SAP’s activity codes mean

The review says what somebody was doing when they were not picking. A code with no line here shows as the code rather than as a guess, because a review page that mislabels somebody’s work is worse than one that makes you ask what DPUT means.

Floor TV

The delivery-line goal the classic board counts towards. It used to be typed on the wall panel itself, which meant a passing finger could move the floor's target and nobody would know who did it or when. It is set here now and the board only reads it.

One-time history backfill

Runs the warehouse task export over past days and files every day it finds into the history, so the week, month and year views have something behind them. The full year is meant to be run once - about an hour of driving SAP, when the floor is quiet; it carries on from where it stopped if SAP drops out, and refuses to be run twice. A day already on file is only replaced when this finds more picks for it. The README says how it works.

Every export asks for four days of creation dates before the first day it files, because a task can sit that long between being created and being picked. So “3 days per export” asks SAP for seven. That lead-in is paid once per export, which is why very small chunks cost more SAP time rather than less - but a wider window is a bigger file for Excel to write, and a slice that runs out of time is skipped. Around a week is the sweet spot on a floor writing fifteen thousand task rows a day.

History collected elsewhere

A backfill drives SAP, and this PC has one session, so while it collects a year of warehouse tasks it is not pulling the floor's exports and the board sits still for hours. Another PC can do the collecting against its own SAP session instead — run Collect history elsewhere.cmd there — and the file it writes is taken in here. Nothing stops. A day this PC watched itself is never replaced by a shorter reading of it.

Backups

The data folder is copied a few minutes after every shift, when SAP stops answering, when this service stops (closing the window included), when a backfill finishes, before anything is restored over it, and every twelve hours if none of those happened - as well as on request. Every copy goes to the cloud copy, sealed, and to a folder on this PC.

And back the other way: every start asks the cloud copy what it is holding, and if that has more history than this PC does, takes it and merges it in - so a host PC that has been away, or a new one entirely, catches up on its own. A merge keeps every day this PC already had. Moving the host to another PC is copying the folder and starting it; fill in cloud.txt beside the program first (see cloud.txt.example) and there is nothing to type here at all.

When SAP falls over

If SAP stops answering, or nothing fresh arrives for the number of minutes below, this PC closes what is left of SAP and opens it again through the Okta tile - which downloads a SAP GUI shortcut that logs itself in - then waits for the session and carries on pulling. It is written to the pull log every time.

The tile usually launches on its own. When it stops on a Sign in button instead, this presses it - buttons only, never a field, so no password is typed. If the wording on your page is something else, put it above; the pull log lists every button it could see each time it tries.
To get the link: open hubbell.okta.com on this PC, find PS1 005 - SCM Production, use the tile's … menu and copy the app link - not the address of the dashboard itself. Nothing is ever closed until that link is set, because a session this cannot reopen is worse than the crash.

The tile is the way in every time. Okta issues a new SAP shortcut whenever it feels like it, so the last one it downloaded is only tried again if SAP falls over within a couple of hours, and only for about a minute before the tile is opened anyway. Saving a shortcut by hand is not a way round Okta for the same reason.

Control folder, and staying up

A folder on this PC that also syncs from somewhere you are - a Google Drive folder works. Drop a file named RESTART SAP.txt (or NO UPDATE.txt), RESTART SERVICE.txt, PULL NOW.txt or BACK UP.txt into it from your phone; the host does it within about fifteen seconds and renames the file to done - ... with what happened inside, which syncs back to you. Blank turns it off. This works even when the cloud copy is the thing that is down.
Staying up. Run tools\install-keepalive.cmd once on the host and a task checks every five minutes that the service is running, and starts it if not. It pauses itself while Apply update.cmd works. That is the only thing that helps when the service itself has died - nothing above can reach a PC that is not running it.

Cloud copy and login

The host pushes the board data to the cloud copy after every change, over outbound HTTPS only, so nothing has to be opened on this PC. The cloud copy is read only; settings and the pull live here.

Monitor tree

Reads every node of the /SCWM/MON tree from the live SAP session so nodes can be chosen by name instead of by recorded position. SAP must be open and logged in on this PC. Click a node to copy its key.

Several nodes are called Warehouse Task and only the path above them tells them apart: loading tasks hang off the delivery, never off a wave. This reads the tree, picks that one and saves it.

How this works

  1. One PC next to SAP runs this. It pulls from SAP about every minute and shares the site.
  2. Everyone else just opens the address below. Nothing to install.
  3. The numbers themselves are under Review data › Get the data, as files or a link Excel can refresh.

Host PC setup

  1. Log in to SAP. In SAP Logon: Options, Accessibility & Scripting, Scripting: tick Enable scripting and untick both notification prompts.
  2. Run Start Staging Lane Health.cmd. It starts this service and opens this page. Run tools\install-autostart.cmd once to have it start at logon (no admin rights needed).
  3. The first time Windows asks whether to allow the service on the network, choose Allow so other PCs can open the board.
  4. Give everyone the address from the Home page. That is the whole viewer setup.

Excel opens each export for a moment because SAP hands the file to it. The service closes that Excel only when it is the sole instance running, so your own spreadsheets are never touched.

If something is wrong

  • SAP not reachable: SAP is closed, not logged in, or scripting is disabled. Check SAP Logon options; if scripting is locked, Basis has to enable sapgui/user_scripting.
  • Pull failing: read the Pull log tab. Each step names itself when it fails. A node that "did not open" usually means the monitor layout changed: use the Monitor tree tab and set the node by label.
  • Wrong file on a status row: the same grid was exported twice under two names. The service keeps the previous good file and says so.
  • Viewers cannot connect: the host firewall blocked the port. Allow node.exe for private networks, or run the service on a different port.
